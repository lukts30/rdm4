## Binary layout results

All original and generated files:

- Have the expected preamble and root payload at `0x1c`.
- Can be scanned from `0x14` to exact EOF using `8 + count * stride`.
  No gap, trailing byte, zero-size block, or partial block was found.
- Have all declared non-null pointers targeting later block payload boundaries.
- Have exactly one known incoming reference per non-root block, with all blocks
  reachable through the known pointer fields.
- Store each block's direct records before its children. Sorting siblings by
  physical position gives a depth-first preorder covering the entire file.

This checks actual pointer fields, not the inspector's inferred matches.
Unknown fields could still conceal aliases; the result is about the recovered
schema. No nonzero sixth root-family pointer or skeleton companion pointer was
found, so these corpora do not exercise those branches of the recovered schema.

Anno 2070 has 3,847 little-endian and 97 big-endian members. All roots are
`1 × 48`. Anno 1800 is entirely little-endian: 15,857 roots are `1 × 48` and
9,320 are `1 × 52`. The extra word in the 52-byte roots was already covered by
an earlier corpus inventory and issue #176. Calling that variant unverified
is no longer appropriate for documentation based on this corpus.

Block headers at odd byte offsets (not divisible by two) occur in 3,885
Anno 2070 and 23,061 Anno 1800 members. This is not an error: blocks follow
one another without alignment padding, so an odd-length payload puts the
next header at an odd offset. The generated files all use 48-byte roots and little-endian storage.

## Inspector findings

The physical scanner passed every tested file. Its inferred edges cannot be
used as proof of sharing, cycles, or a semantic tree:

| Corpus    | Files with apparent multiple forward incoming edges | Extra forward matches beyond known pointers | Files with backward/self candidates |
| --------- | --------------------------------------------------: | ------------------------------------------: | ----------------------------------: |
| Anno 2070 |                                                 166 |                                         617 |                                 695 |
| Anno 1800 |                                                 623 |                                       1,824 |                               5,130 |

All 2,441 extra forward matches have now been classified by their source
record and byte range. The second scan reproduces the inspector's extra-match
count for every file:

| Classification                                          | Matches |
| ------------------------------------------------------- | ------: |
| Entirely within known scalar/vertex data                |   2,246 |
| Overlap known pointer fields at a different byte offset |     157 |
| Cross the end of a bounds float into following bytes    |      38 |
| Entirely within unknown fields                          |       0 |

The 38 bounds overlaps comprise eight model records at relative offset 50
and 30 bone records at relative offset 58. Bone offsets 36–59 contain bounds,
although rdm4 still names that region padding. A fresh fetch of `origin/master`
on 2026-10-21 confirms revision `901a951`: `Meta` names model bounds, but
`RdmJoint` still stores all 48 bytes after `parent_id` as `_padding`. The
identified bone bounds occupy the first 24 bytes of that padding. The matches at offset 58 combine
the last two bytes of the final bounds float with two following bytes. They
are not additional pointer fields under the recovered record layouts.
This classification does not rely on absolute alignment or assume that every
unknown field is padding. It finds no missed pointers among these candidates;
it does not prove the meaning of every unknown byte in the format.

Run `python3 classify_matches.py /path/to/audit-results` to reproduce.
`extra-matches.jsonl` records every source file, record, field offset, target,
and classification; `extra-matches-summary.json` contains the totals.

Example: `Data2.rda/data/graphics/animals/air/eagle/anim/eagle_idle01.rdm`
contains three false forward matches at file offsets `0x1f81`, `0x2161`, and
`0x25c1`, each equal to payload address `0x31bf`. They start at byte 22 of
animation-frame records, inside float data, not in pointer fields.

`EdgeConfidence::Strong` has been renamed to `EdgeDirection::Forward`;
backward/self matches use `EdgeDirection::BackwardOrSelf`. Both display as
candidates. Block IDs now use a distinct `BlockId` type, with explicit vector
index conversion, while byte offsets remain `usize`. Display the physical block list (offset, count, stride,
and end) separately from candidate references and schema-identified pointers.
Do not silently discard unaligned matches, since absolute block alignment is
not guaranteed.

The forward-candidate traversal reaches every block in all 29,176 tested files;
there are no unreachable-block exceptions. The separate known-pointer traversal
also reaches every block. Neither result alone establishes that all candidate
references are real or that the pointer schema is complete.

Other code-review observations:

- The scanner validates framing with checked size arithmetic and rejects
  incomplete payloads. It does not validate root record count/width.
- A mismatching preamble root offset produces a warning, but root navigation
  still assumes block zero. This is a diagnostic assumption, not support for
  arbitrary roots.
- `forward_reachable()` scans the entire edge list for every visited block;
  the batch example uses adjacency lists. This does not alter parsed edges.
- `every_repository_fixture_forms_a_reachable_tree` asserts that the number
  of forward candidates equals `blocks - 1`. Adding the valid eagle fixture
  would fail that assertion. Tree tests need declared pointers, not matches.
- Existing inspector tests passed. Six added audit tests cover complete trees,
  sharing, scalar collisions, unreachable blocks, trailing data, and overflow.

## Newly reproduced failures and compatibility risks

“New” here means not found in the fetched repository issue list. Some risks
were already mentioned in code comments or the disassembly notes. Nothing has
been posted to GitHub by this audit.

### 1. Zero-weight source vertices produce NaN glTF weights

Five unique Anno 1800 skinned models contain 55 vertices whose weights sum to
zero. These are genuine source files, not malformed test mutations.

Reproduction: export with `-s`:

`data25.rda/data/graphics/portraits/residents/resident_colony_tier01/rdm/resident_colony_tier01_lod1.rdm`

The converter returns success. Its GLB contains 336 non-finite weight
components: 21 vertices × 4 components × 4 weight sets. The Khronos validator
reports `ACCESSOR_INVALID_FLOAT` and additional joint-index errors.
`gltf_export::put_joint_weight` divides by a zero total weight.

**Fix direction:** define a zero-weight policy or reject the input explicitly;
do not emit NaNs. The appropriate in-game fallback has not been established.

### 2. Additional joint/weight sets are silently lost on import

Anno 1800 has 154 model records declaring 15 or 16 influences, with four
joint and four weight components. The maximum nonzero influence count observed
in the deduplicated skin scan is 14; “16” is not necessarily the count used by
every vertex. All active joint indices fit their selected skeletons.

The source format is
`P4h_N4b_G4b_B4b_T2h_I4b_I4b_I4b_I4b_W4b_W4b_W4b_W4b`:
56 bytes per vertex, four joint sets followed by four weight sets, with a
declared influence count of 15. It has 335 vertices, 36 bones, and one material
group. The destination format has 32-byte vertices and one joint/weight pair;
the writer declares one influence. Both conversion commands exit successfully.
The intermediate GLB has zero validator errors and zero warnings.
Full descriptors, commands, validation output, and all 335 vertices' input and
output skin attributes are saved as `kraken-full.json` in the result directory.

`data11.rda/data/dlc01/graphics/units/wildlife/kraken/rdm/kraken_lod2.rdm`
exports valid glTF with `JOINTS_0..3` and `WEIGHTS_0..3`. Importing it to
`P4h_N4b_G4b_B4b_T2h_I4b_W4b` succeeds but reads only set zero. One of the
335 output vertices consequently has no remaining weight at all.

Direct inspection of the exported GLB shows 52 vertices with nonzero weights
outside set zero, and a maximum of 11 active influences on a vertex. Vertex 56
(zero-based) has zero weights in set zero; its four active influences are all
in set one: joints `[2, 7, 4, 1]`, with weights approximately
`[0.023715, 0.296443, 0.328063, 0.351779]`. Those four influences would fit the
destination format, but the importer never reads them. The resulting vertex has
four zero weights. This is more than the unavoidable loss from reducing vertices
with more than four influences.

**Fix direction:** explicitly reject unsupported additional sets or implement
an intentional influence-reduction policy. A destination with four slots
cannot preserve all source influences, but silent truncation is avoidable.

### 3. A valid glTF joint index 256 becomes zero

The controlled `joint256-explicit/input.gltf` has 257 joints, a common joint
root, explicit identity inverse-bind matrices, and valid `UNSIGNED_SHORT`
joint indices. The Khronos validator reports zero errors.

rdm4 succeeds, but `[256, 1, 2, 3]` becomes `[0, 1, 2, 3]` in the RDM vertex.
The cause is the unchecked `as u8` casts in `vertex_transform::i4b`.
This risk was mentioned in the earlier research notes; this audit supplies a
valid, independently validated reproduction.

### 4. Generated bone order differs from every original skeleton checked

No original skeleton has a non-root parent at or after its child index.
Fourteen round-tripped files have 23 such parent references.

Small example: `carrier_crew_03_toolbox_lod0.rdm` (`source-001` in the
conversion manifest) gains a bone at index 0 whose parent is index 1.
`gltf_reader::create_joints_from_non_skin_nodes` appends promoted parents.

The examined Anno 2070 animation routine computes global matrices in one
forward loop and reads the parent's global matrix during the child's step.
This makes output bone order a compatibility concern. No game rendering test
was performed, and possible reordering elsewhere has not been ruled out.

**Fix direction:** investigate topological bone ordering and remap vertex
indices and animation references together. Do not confuse this parent-index
ordering with the file's block-reference tree; the latter still passes.

### 5. Optional inverse-bind matrices cause an import panic

All three controlled glTF inputs without `inverseBindMatrices` validate with
zero errors, but skinned import panics at
`read_inverse_bind_matrices().unwrap()`.
The [glTF specification](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#skins-overview)
defines identity matrices when this property is absent.

### 6. Generated influence metadata disagrees with the vertex data

The explicit four-weight test writes `[64, 64, 64, 64]`, summing to 256, while
the vertex-format link says one influence. The high-level writer sets that
field to one whenever a model has a skin, rather than computing the maximum
number of active influences per vertex. One `I4b`/`W4b` pair contains four
joint/weight slots; the metadata counts influences, not attribute sets.

The input weights are `[0.25, 0.25, 0.25, 0.25]`. Each is independently encoded
as `round(weight * 255)`: `round(63.75) = 64`. Their byte sum is therefore 256,
which decodes to approximately 1.00392 when divided by 255. The metadata mismatch
(four active influences but a declared count of one) and the rounding surplus
are separate issues. The audit does not establish the game's response to either.

All original skinned models checked have observed active-influence counts at
or below that metadata value. The field's count interpretation is supported
by the older executable analysis and by the larger corpus; it is not a shader
ID. Correct metadata and a deliberate weight-quantization policy are separate
from framing correctness. The research notes already identified the metadata
risk; this run confirms the generated mismatch.

### 7. A skeleton alone does not imply skinned vertex attributes

`harboursystem_ground_01.rdm` and `equip_skateboard_lod0.rdm` export with `-s`
but their meshes have no joint attributes. The resulting GLBs fail validation
with `NODE_SKIN_WITH_NON_SKINNED_MESH`; importing them with `-s` also fails.
The raw RDM structure is valid. The export path needs to distinguish a skeleton
record from a mesh that actually supplies skinning attributes.

## Coverage and limits

The 57 real-model export attempts yielded 53 GLBs; 46 round trips completed.
Four unskinned synthetic formats and five explicit-skin model/animation outputs
bring the generated RDM count to 55. All six target vertex formats were
exercised. The two color sets in the controlled two-color format stayed distinct.

All 60 generated glTF/GLB inputs and intermediates were checked with the
repository's Khronos validator (`2.0.0-dev.3.3`): six controlled glTF inputs
passed; three exported GLBs failed for the reasons above.

The semantic audit checks descriptor widths, index types and ranges, triangle
group ranges, material/skeleton indices, finite ordered model bounds, bone
parent ranges, duplicate bone names, and monotonic frame times. It does not
prove rendering equivalence, physical coordinate conventions, bind-pose
correctness for every asset, animation interpolation, or game acceptance of
shared/backward block references. No runtime override order was inferred.

The report contains no disassembly traces. Raw per-file results, conversion
commands, hashes, and validator reports remain in
`/tmp/rdm-layout-audit-20261021/`; see the adjacent README for rerunning.

The packaged runner was rerun from this worktree into a fresh directory. All
three corpus summaries and every conversion exit status reproduced. The 19
inspector tests and six audit tests pass.

## Rust incoming-reference verification

The Rust `corpus` example now traverses recovered pointer fields separately
from inferred candidates. It counts every edge before visited-target filtering
and checks root indegree zero, every other indegree one, and full reachability.
Rerunning all 29,176 files produced zero missing or multiple known incoming
references, zero incoming root references, zero unreachable blocks, and zero
schema errors. Existing candidate columns are unchanged from the earlier run.
Results are saved as `*-rust-known.tsv` in the result directory.

Three Rust example tests cover duplicate references, a disconnected cycle,
and duplicate schema pointers to one payload. They pass, as do the existing
19 inspector tests and Clippy for the example.
